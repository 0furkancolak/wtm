## How a W2 unit proves itself

W1-4 landed the evidence path. Each unit dispatches CI against its own branch with its cluster's
test list and must show that list green on the win32 leg inside the 25 minute cap:

```bash
gh workflow run CI --ref claude/<unit> -f win32_test_filter="<the unit's list below>"
```

On such a run the win32 leg is **not** `continue-on-error` — the targeted tests decide the result —
the other four legs skip every step after checkout, and the win32 leg runs the targeted tests before
lint and typecheck so a red lint cannot cost the run its evidence.

Ordinary merge conditions are unchanged: every non-win32 job green on the head commit.

## The one number that shapes this wave

## W2-1 — 9a: DaemonClient frame decoder hangs

Two tests hang for the full 300s per-test bound and reproduce identically in both runs, burning ~10
minutes of every win32 run between them:

- `packages/cli/src/__tests__/client.test.ts`
  - `DaemonClient > uses a fresh frame decoder after a partial frame corrupts the first connection` — 301036ms / 301042ms, then `Received promise that rejected`
  - `DaemonClient > reconnects immediately with a fresh decoder after an oversized frame header` — 301027ms / 301041ms, same

Both are about the decoder's state after a *bad* frame, and both wait forever rather than failing, so
the client is not noticing a condition it notices on POSIX. Find the root cause — a read that never
completes, a socket event that does not arrive on a named pipe, or a decoder reset that never runs —
rather than bounding the wait.

Code area: `packages/cli/src` daemon client framing, `packages/protocol` codec. Depends on W1-2 and
W1-4 (both merged).

Filter:
```
packages/cli/src/__tests__/client.test.ts packages/protocol/src/__tests__/ipc-framing.test.ts packages/protocol/src/__tests__/ipc.test.ts
```

## W2-2 — 9c: batch or persist the PowerShell ACL checks

The strongest evidence in the logs is a *passing* file: `logs.test.ts` above. The trust path shells
out to a real `pwsh.EXE` per call, and a cold PowerShell process costs on the order of a second to
start and import `Microsoft.PowerShell.Security`. ci.yml already carries a comment saying the
300000ms win32 test timeout is a stopgap and that a pooled or long-lived session is the real answer.
This unit is that answer.

One real failure sits in the same seam:
- `packages/daemon/src/__tests__/anchor-log-trust.test.ts` — `a parent swap while ACL authorization waits cannot publish into the replacement directory` → `ANCHOR_LOG_CLOSED` (22ms / 28ms) in both runs. Its two neighbouring Windows-ACL tests pass, so the failure is specifically the swap-while-authorization-is-in-flight window.

Low-confidence, decide whether to take it: `packages/daemon/src/__tests__/main.test.ts > names the
privacy grant only for a directory that exists and refuses to open` — the fixture denies read access
POSIX-style, Windows ACLs do not deny it, and the daemon falls into its slow-filesystem branch. It
touches the same permission seam; if this unit does not take it, it belongs with 9g.

Whatever the mechanism (a batched `Get-Acl` over many paths, or one long-lived session reused across
calls), it must not weaken the trust answer: the point of the check is refusing a path another
principal can write. Say in the brief's report what the pooling does on session death and whether a
reused session can be influenced between calls.

Code area: `packages/platform/src/trust/*`, core log store. Depends on W1-4 (merged).

Filter:
```
packages/platform/src/trust/__tests__/windows.test.ts packages/platform/src/trust/__tests__/windows-acl-batch.test.ts packages/platform/src/trust/__tests__/windows-powershell.test.ts packages/platform/src/trust/__tests__/posix.test.ts packages/daemon/src/__tests__/logs.test.ts packages/daemon/src/__tests__/anchor-log-trust.test.ts packages/daemon/src/__tests__/main.test.ts packages/core/src/__tests__/file-trust-guard.test.ts
```

**Note for this unit only:** `packages/core/src/__tests__/file-trust-guard.test.ts` pins an invariant
that `packages/core/src/file-trust-policy.ts` and `packages/platform/src/trust/posix.ts` carry
textually identical predicates, and that `packages/platform/src/trust/windows.ts` deliberately keeps
the stricter `nlink === 1`. W1-1 landed that. Do not "unify" the Windows predicate to match POSIX —
read the reasoning in `windows.ts` first.

## W2-3 — 9f: Windows SQLite/state path, disk and gc

Two distinct root causes, both reproducing in both runs:

1. **The resource guard cannot establish the current user identity.** `ResourcePathGuardError: The current user identity is unavailable.` (`RESOURCE_PATH_DENIED`, from `core/src/resources/guard.ts:187` `createResourceGuard`) fails all four `gc.test.ts` tests and `remove-runtime.test.ts > deletes the ephemeral resources it materialized instead of refusing over them` (`exitCode: 3`, `worktreeExists: true`). Windows has no `getuid`.
2. **SQLite under a private parent.** `adapter.test.ts` fails three ways — `Adapter trust command unexpectedly failed` (exit 1), the concurrent variant, and `ENOENT lstat 'C:\…\missing\WTM\state.db'` (errno -4058) for `creates the missing private WTM state parent before opening SQLite`. `cli/src/__tests__/main.test.ts > wires adapter trust through the CLI with an injected SQLite database path` exits 1 on the same path. `runtime-factory.test.ts` adds two `PrivateDirectoryError` failures from `assertNoSymlinkComponents` (`core/src/state/private-directory.ts:131`).

Also in this cluster:
- `cli/src/__tests__/daemon-status.test.ts > daemon-status.json round-trips through one private file` → `Expected: 384, Received: 438` (0o600 vs 0o666 — the POSIX mode check has no Windows meaning).
- `cli/src/__tests__/reconcile-fallback.test.ts > still ends in one coded envelope when the registry cannot be written at all` → `Expected "WTM_NOT_INITIALIZED", Received null` (21-24s): making the registry unwritable does not produce the coded refusal on Windows.

Code area: core `state/*`, `resources/gc.ts`. Depends on W1-4 (merged).
